# Data modelling

## Three layers

Every Delta table belongs to one of three layers. Naming carries the
layer:

| Layer | Catalog / schema | What lives there |
|---|---|---|
| **Bronze** | `cdo_<env>.bronze.<source>__<table>` | Raw, append-only, schema-on-read tolerated. One row per source event. |
| **Silver** | `cdo_<env>.silver.<domain>__<table>` | Cleaned, typed, deduplicated. One row per business entity, slowly-changing handled. |
| **Gold** | `cdo_<env>.gold.<consumer>__<table>` | Aggregated, denormalised for a specific consumer (BI tool, ML feature store, dashboard). |

Cross-layer reads are fine downward (gold reads silver); upward reads
(silver reads gold) are forbidden.

## Partitioning

- **Time-series tables**: partition by `event_date` (DATE), not
  `event_ts`. Daily partitions hit the sweet spot — files are large
  enough to avoid the small-file problem, small enough that compaction
  finishes in minutes.
- **Don't over-partition.** A partition with < 1 GB of data is too small.
  Combine columns or drop the partitioning.
- **Never partition by high-cardinality columns** (`customer_id`,
  `transaction_id`). Use Z-ORDER instead.
- **Liquid clustering is the modern default** for new tables — let
  Databricks pick partitioning dynamically. Specify clustering columns
  that you filter or join on.

## Primary keys + constraints

- **Every fact and dim table declares a primary key** in its `bundle.yml`
  table config. Unity Catalog tracks it (informational).
- **Surrogate keys are `BIGINT` generated by `monotonically_increasing_id()`
  or a UUID** — never the source's natural key.
- **Foreign-key constraints are documented in `AGENTS.md`** of the
  consuming project. They are not enforced at write time.

## Schema evolution

- **Additive changes (new columns) are safe.** They land via `mergeSchema`.
- **Renames and type changes go through a new column + deprecation:**
  add the new column, dual-write for 2 weeks, switch readers, drop the old.
- **Breaking changes require an ADR.** Document the consumers and the
  migration plan.

## Idempotency

- **Every batch write is idempotent.** Re-running yesterday's job should
  produce the same table state.
- **Use `MERGE INTO ... WHEN MATCHED` on the natural key** for upserts.
- **Streaming writes use `foreachBatch` with deterministic micro-batch IDs.**

## Late-arriving data

- Watermarks are documented in the AGENTS.md of the consuming project.
- Reprocessing windows: bronze keeps 30 days append-only, silver
  recomputes from bronze for the last 7 days nightly, gold reads silver
  with no late-arrival window.

## Naming columns

| Pattern | Example |
|---|---|
| `<noun>_id` | `customer_id` |
| `<noun>_at_<tz>` | `created_at_utc`, `updated_at_sgt` |
| `is_<adjective>` | `is_active`, `is_deleted` |
| `<noun>_count` | `transaction_count` |
| `<noun>_amount_<ccy>` | `payment_amount_sgd` |

## What we deliberately do NOT do

- **No nested structs deeper than 2 levels.** Flatten — BI tools struggle.
- **No SCD Type 2 unless explicitly justified.** It doubles the storage
  and query complexity. Most "history" requirements are met by a snapshot
  table partitioned by `as_of_date`.
- **No `string` for booleans, dates, or numbers.** Use the right type.
